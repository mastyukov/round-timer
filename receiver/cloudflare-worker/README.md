# Cloudflare Receiver Round Timer — актуальное состояние

**09.11.2026.** Рабочий Worker существует и был опубликован ранее: https://round-timer-error-receiver.mastyukov.workers.dev/v1/error. Исторически подтверждённый release-run: `42508397821`. Он принимает четыре фиксированных поля ошибки с одобренных Origin и записывает их в Analytics Engine `round_timer_error_events`. Origin не обеспечивает аутентификацию отправителя. Общий rate limiter ограничивает поток приблизительно 60/мин по локациям.

**PR №4 НЕ изменяет работающий Worker.** В ветке находится только проект расширения для v0.8.6-rc1.

## Контракт нового кандидата

- HTTPS POST `/v1/error` с `text/plain;charset=UTF-8`, `mode:cors`, `credentials:omit`.
- Дополнительно к четырём проверенным кодовым полям — случайный UUIDv4 `eventId` **отдельной ошибки**, не ID пользователя или устройства.
- Сервер проверяет CORS Origin и синтаксис ID. В `Analytics Engine` продолжает записывать только **четыре поля**, а не UUID. Возможна проверка независимым агрегированным SQL, но HTTP 204 не доказывает окончательное долговременное хранение.
- Серверный `ERROR_DEDUP_KV` держит только временный ключ `round-timer-event:<UUID>` до 24 ч. Повтор того же ID без новой записи отвечает 204. При отсутствии KV binding новая форма запроса получает 503; старый четырёхпольный формат поддерживается.
- KV eventual consistency: одновременные запросы в разные локации Cloudflare могут дать двойную запись; строгой exactly-once гарантии нет. Без платного сервиса или дополнительной транзакционной координации гарантия не предусмотрена.
- При ошибке KV или отсутствующем rate limiter Worker не записывает данные и отвечает 503. Передаваемые поля с PII отбрасываются проекцией.

## Конфигурация — только после отдельного разрешения

1. Создать в Cloudflare **новый отдельный KV namespace** для краткоживущих кодов ошибок, проверить бесплатные лимиты и доступный объём.
2. Добавить только идентификатор этого пространства (не секрет) к `receiver/cloudflare-worker/wrangler.jsonc` под binding `ERROR_DEDUP_KV`. Пока его нет намеренно, чтобы не менять действующую инфраструктуру.
3. Проверить новую версию локально и в изолированной среде на синтетике, включая CORS, квоты, ID-дедупликацию, отказы и рабочий обратный контракт.
4. Отдельно одобрить выпуск Worker; **только после этого** рассматривать выпуск PWA с локальной очередью.
5. При проблеме с рабочим приёмником откатиться на прежнюю проверенную Worker-версию `42508397821`; вернуть PWA v0.8.5, если уже выпущена новая версия.

## Фактическая проверка до развёртывания

Все новые тесты — Node.js с синтетическим Worker, поддельным KV, Analytics Engine и фиксированными кодами. Они **не доказывают** работу нового binding на реальном Cloudflare. Сетевые данные (в частности IP) могут технически обрабатываться Cloudflare, но не сохраняются в Analytics Engine кодом приложения.
